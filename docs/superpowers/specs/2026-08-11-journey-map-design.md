# Journey Map Design

**Status:** approved, pending implementation plan.

## Goal

A read-only "you are here" screen showing the player's progress along the
caravan route, reached from a new fourth button on `MainMenu.tscn` (New
Game / Continue / **Map** / Quit). This is the second of the two GUI
sub-projects split out when the user first asked to "generate gui" - the
main menu (first sub-project) is already shipped on master. Passive
display only: no navigation, no chapter-select, no replay. Reuses the
location background PNGs already generated by the pixellab pipeline as
waypoint thumbnails - no new art.

## Route model: two flat lists sharing a prefix, not a generic branch engine

The campaign isn't a single line. Farah forks into two routes of
different length:

- **Main route:** Herat (04a) → Pushang → Sarakhs → *optionally* Merv →
  Nishapur (ending)
- **Favor route:** Herat Favor (04b) → Plunder Ending directly - skips
  Pushang, Sarakhs, and Merv entirely

This is the only fork and the only optional detour in the whole,
completed campaign - there will never be a third branch. A generic
tree-traversal system would be solving a problem this project doesn't
have. Instead, `content/map/route.json` authors the shape directly:

```json
{
  "display_names": {
    "chapter_00_prologue": "Ghazni",
    "chapter_01_teginabad": "Teginabad",
    "chapter_02_bost": "Bost",
    "chapter_03_farah": "Farah",
    "chapter_04a_herat": "Herat",
    "chapter_04b_herat_favor": "Herat",
    "chapter_06_pushang": "Pushang",
    "chapter_07_sarakhs": "Sarakhs",
    "chapter_07b_merv": "Merv",
    "chapter_08_nishapur": "Nishapur",
    "chapter_05_plunder_ending": "Plunder"
  },
  "shared_prefix": [
    "chapter_00_prologue",
    "chapter_01_teginabad",
    "chapter_02_bost",
    "chapter_03_farah"
  ],
  "fork": {
    "main": "chapter_04a_herat",
    "favor": "chapter_04b_herat_favor"
  },
  "main_suffix": [
    "chapter_06_pushang",
    "chapter_07_sarakhs",
    {"chapter_id": "chapter_07b_merv", "optional": true},
    "chapter_08_nishapur"
  ],
  "favor_suffix": [
    "chapter_05_plunder_ending"
  ]
}
```

`shared_prefix` always occurs, in every playthrough that reaches that far
- every entry is safe to preview as an unreached waypoint ahead of time.
After the fork, only the suffix matching the branch actually taken is
ever real for that playthrough, so nothing from the other suffix is ever
shown, previewed, or hinted at.

## `JourneyMapBuilder`: a pure, testable engine class

New `engine/map/JourneyMapBuilder.gd`, matching this project's existing
engine-layer convention (`DialogueEngine`, `Ledger`, `ReputationTracker`):
plain `RefCounted`, no `FileAccess` calls of its own. It takes already-
parsed data and returns a plain `Array` of waypoint dictionaries - the
scene layer does all the file I/O and hands in the results, the same
separation `SaveManager` (file I/O) vs `GameState` (pure data) already
establishes elsewhere in this codebase.

```gdscript
class_name JourneyMapBuilder
extends RefCounted

# route_data: the parsed content of content/map/route.json
# visited_chapter_ids: Dictionary used as a set - keys are chapter ids with
#   an existing user://borrowed_fortune_<id>.json save file
# current_chapter_id: the pointer file's chapter_id, or "" if there is
#   none (a fresh game, or a finished playthrough - the pointer is cleared
#   on a true ending, see the main menu design's Continue section)
func build_waypoints(route_data: Dictionary, visited_chapter_ids: Dictionary, current_chapter_id: String) -> Array:
	...
```

Each returned waypoint: `{"chapter_id": String, "display_name": String,
"status": "current"|"visited"|"unvisited", "is_ending": bool}`.

**Algorithm:**

1. Walk `shared_prefix` in order. For each id: `status` is `"current"` if
   it equals `current_chapter_id`, else `"visited"` if
   `visited_chapter_ids.has(id)`, else `"unvisited"`. Every prefix entry
   is always appended, regardless of status - the whole prefix is
   deterministic for every playthrough, so previewing it dim ahead of
   time reveals nothing about future choices.
2. At the fork: if `fork.main` is visited or current, append it (status
   as above) and continue walking `main_suffix`. Else if `fork.favor` is
   visited or current, append it and walk `favor_suffix` instead. Else
   (neither reached yet) - stop. Nothing is appended for the fork or
   beyond; the caller sees the spine end cleanly at Farah. This is the
   only stopping condition in the whole algorithm.
3. Walking a suffix: for each entry, resolve its id (a bare string, or an
   object's `"chapter_id"` field) and its `optional` flag (`false` unless
   the entry is an object with `"optional": true`). Compute `status` the
   same way as step 1.
   - Non-optional entries always append, same reasoning as the prefix -
     once the fork is resolved, the rest of that specific route is
     deterministic (aside from Merv, which is handled separately below).
   - Optional entries append only when `status` is `"current"` or
     `"visited"`. An unvisited optional entry is silently omitted and
     does **not** stop the walk - Sarakhs still previews Nishapur as the
     next dim waypoint regardless of whether Merv ever happens, since
     Merv's presence or absence doesn't change what comes after it.
4. `is_ending` is `true` for exactly the last entry of `main_suffix`
   (Nishapur) and the last entry of `favor_suffix` (Plunder Ending) -
   structurally tagged regardless of status. The scene layer only applies
   the special "Journey's End" visual when `is_ending` is true **and**
   `status != "unvisited"` - an unreached ending still just previews dim
   like any other future waypoint, the distinct marker only appears once
   the player actually gets there.

A finished playthrough (pointer cleared, `current_chapter_id == ""`)
naturally falls out of this same algorithm with no special case: no
waypoint ever matches an empty string, so nothing gets `"current"` -
every reached chapter (including the ending, which always has its own
save file too, same as every other chapter) shows as plain `"visited"`,
and the ending one still gets its `is_ending` marker.

## Scene: `JourneyMapScreen`

New `scenes/journey_map/JourneyMapScreen.tscn` + `.gd`. Reads
`content/map/route.json` (same raw-`FileAccess`-and-`JSON.parse_string()`
pattern `ChapterView.load_chapter_by_id()` already uses for
`manifest.json`), derives the full list of chapter ids to check
(`shared_prefix` + `fork.main` + `fork.favor` + every id in
`main_suffix`/`favor_suffix`) directly from the parsed route data rather
than a second hardcoded list, and checks
`FileAccess.file_exists("user://borrowed_fortune_%s.json" % id)` for
each to build `visited_chapter_ids`. Reads the pointer file
(`user://borrowed_fortune_current_chapter.json`) for `current_chapter_id`
using the same small inline pattern `Main.gd`'s `_read_pointer_file()`
already uses - this project's existing convention is a local copy of this
~8-line snippet per script that needs it (`ChapterView`, `MainMenu`, and
now this), not a shared utility, so this follows precedent rather than
introducing a new one.

Calls `JourneyMapBuilder.new().build_waypoints(...)` and renders the
result as a horizontal row of `TextureRect` thumbnails
(`mouse_filter = 2`, same discipline as every other decorative art node
in this project), each loaded via the same raw
`FileAccess.file_exists()` + `Image.load_from_file()` +
`ImageTexture.create_from_image()` pattern as `ChapterView._update_background()`
and `MainMenu._update_background()`, from
`res://assets/backgrounds/<chapter_id>.png`. Per waypoint:

- `"unvisited"` - thumbnail's `modulate` set to `Color(0.5, 0.5, 0.5, 0.55)`
  (a gray tint plus reduced alpha) - approximates the mockup's
  dim/grayscale treatment using a plain `TextureRect` property, with no
  `ShaderMaterial` needed. This project doesn't use shaders anywhere
  else; a real desaturation shader would be new rendering infrastructure
  for one screen, out of proportion to what a "dim, clearly-not-reached"
  cue needs.
- `"visited"` - full color (`modulate` left at its default
  `Color(1, 1, 1, 1)`).
- `"current"` - full color, plus a small "you are here" marker
  (implementation detail left to the plan - e.g. a border or a small
  icon overlay).
- `is_ending` waypoints with a non-`"unvisited"` status also get a
  distinct marker (e.g. a different border style and the label "Journey's
  End" instead of the plain display name).

A `BackButton` returns to `MainMenu.tscn` via
`get_tree().change_scene_to_file(...)`, the same call `MainMenu.gd`
already uses for its own scene changes.

## `MainMenu.gd` change: a fourth button, correctly gated

`MainMenu.tscn` gains a `MapButton` in `ButtonsContainer`, between
`ContinueButton` and `QuitButton`. **Its disabled condition is not the
same as `ContinueButton`'s**, despite both looking like "is there
progress" checks: `ContinueButton` is disabled when the pointer file is
absent, but the pointer is deliberately *cleared* once a true ending is
reached (see the main menu design's Continue section) - a player who
just finished the game would have `ContinueButton` correctly disabled
*and* a full journey worth of completed chapters to look back on. Gating
`MapButton` on pointer-file existence would wrongly hide the map from
someone who just finished playing.

`MapButton.disabled` is instead true only when **none** of the route's
chapter ids have a save file at all - a real "nothing has happened yet"
check, independent of whatever the pointer currently says:

```gdscript
func _map_button_should_be_disabled(route_data: Dictionary) -> bool:
	for chapter_id in _all_chapter_ids_in_route(route_data):
		if FileAccess.file_exists("user://borrowed_fortune_%s.json" % chapter_id):
			return false
	return true
```

(`_all_chapter_ids_in_route()` is the same id-extraction logic
`JourneyMapScreen.gd` needs - the exact shared helper/duplication
decision is left to the implementation plan, but it must not depend on
`ContinueButton`'s own check.)

## Testing

- `JourneyMapBuilder` gets its own unit tests, driven entirely by
  synthetic `visited_chapter_ids` dictionaries and a small in-test
  `route_data` literal - no real save files or `content/map/route.json`
  needed for most cases. Covers: prefix-only preview before the fork
  resolves; main-route resolution and full suffix walk; favor-route
  resolution (shorter path, no Pushang/Sarakhs/Merv ever appearing);
  Merv present vs. silently skipped without stopping the walk; the ending
  marker on both possible endings; the finished-game case
  (`current_chapter_id == ""` with a full visited set, no waypoint marked
  `"current"`).
- `JourneyMapScreen` gets a thinner test in the same shape as
  `test_main_menu.gd` - constructing the scene against a fixture route
  file and fixture save files, asserting the resulting waypoint count and
  a couple of specific statuses render as expected, not a pixel-level
  render check.
- `MainMenu.gd`'s new `MapButton` gating gets tests parallel to its
  existing `ContinueButton` tests, specifically including the case that
  motivated the different gating rule: pointer absent, but a real
  finished-game save file exists - `ContinueButton.disabled == true`,
  `MapButton.disabled == false`.

## What this pass does not do

- No navigation, chapter-select, or replay from the map - confirmed,
  passive display only.
- No fork or "road not taken" ever drawn - confirmed, the map only ever
  shows the single path actually walked, plus the deterministic prefix
  ahead of any unresolved fork.
- No placeholder for ambiguous slots (Herat variant, Merv, ending) before
  they resolve - confirmed, the spine simply stops rather than hinting at
  what's ahead.
- No new art - reuses the 11 existing `assets/backgrounds/*.png` files
  generated in the earlier pixellab backgrounds pass.
